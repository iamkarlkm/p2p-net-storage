# 文件同步完善度总结报告

更新时间：2026-07-26

## 1. 报告目的

本文档总结 `p2p-sync` 文件同步能力的当前完善度，覆盖以下内容：

- 当前主链路能力边界
- 已完成增强项与验证状态
- 仍然存在的功能缺口与工程风险
- 建议的后续优先级

本文档基于当前工作区状态编写，既包含已提交改动，也包含当前工作区内已验证但尚未提交的 monitor 展示调整。

## 2. 结论摘要

整体判断：项目的文件同步能力已经从“可用但脆弱”提升到“具备可验证闭环、具备基础冲突治理与监控可观测性、仍有进一步工程化空间”的阶段。

简要结论如下：

- P0 级核心闭环已经补齐：
  - 真实双节点 E2E 已覆盖
  - `PUT_FILE` 的内容校验与 finalize 语义已加固
  - rename/move 语义已明确为 `DELETE old + CREATE new`
- P1 级主链路增强已完成主要部分：
  - 多 endpoint 已从轮询单发升级为 fan-out 多副本分发
  - 冲突处理已从硬编码失败升级为策略化处理
  - 自动重试已从无限重试演进为“限次 + 退避”
- P2 级可观测性建设推进明显：
  - 上传中状态、分片进度、最近完成/失败历史、失败聚合统计、热点失败项、队列矩阵、最近时间线、首页结构重排均已落地
  - 当前工作区还补上了 failed 项的“可重试资格/剩余次数”展示
- 尚未完全收口的部分主要集中在：
  - 多节点更强验证覆盖
  - 更策略化的人工/自动恢复建议
  - 更显式的大文件策略层
  - 失败项分级处置和趋势分析

## 3. 当前能力概览

### 3.1 同步主链路

当前 sender/receiver 主链路已经具备以下能力：

- 目录扫描 + WatchService 持续监听
- 文件/目录事件分队列处理
- 同 `fileId` inflight 串行化，避免 `CREATE`/`MODIFY` 重叠冲突
- RPC 发送端 apply -> upload -> finalize 两阶段语义
- finalize 前重读源文件 `lastModified`，降低时间戳漂移导致的误提交风险
- 上传后通过 MD5 进行内容强校验
- 接收端 pending path owner 管理与冲突策略接入

### 3.2 目录与事件语义

当前事件语义已经明确或修正为：

- Windows rename/move 语义按 `DELETE old + CREATE new` 处理
- 启动扫描与 watch 事件都支持 `includeGlobs` / `excludeGlobs`
- 状态表 startup/active 切换问题已修复，不再因为集合引用交换导致事件丢失

### 3.3 分发与冲突治理

当前已具备：

- 多 endpoint fan-out 多副本分发
- 聚合 ACK 语义：全部成功才成功；有失败优先失败；否则按 retry 处理
- 冲突策略可配置：
  - `FAIL_FAST`
  - `LAST_WRITE_WINS`

### 3.4 重试与失败治理

当前已具备：

- `retryCount` 统计
- `failedAtMillis` / `lastRetriedAtMillis`
- 自动重试最大次数 `maxRetryCount`
- 自动重试退避时间 `retryBackoffMillis`
- monitor 层展示 failed 项的：
  - `retryable`
  - `remainingRetries`

注意：

- 自动重试现在受“限次 + 退避”控制
- 人工在 monitor 页面触发的重试不受该限制，仍然允许人工介入强制再试

## 4. 已完成增强项

### 4.1 P0 级

已完成：

- 真实双节点目录同步 E2E 测试
- finalize 后内容校验闭环
- rename/move 语义澄清与回归测试
- `STD_ACCEPTED` 被误判为最终响应的问题修复
- 运行时线程池初始化缺失导致的服务端 NPE 修复

价值：

- 解决了“测试看起来存在，但真正双节点同步并不稳”的问题
- 解决了长耗时上传链路可能提前结束的问题
- 解决了 rename 语义与状态存储切换错误导致的丢事件问题

### 4.2 P1 级

已完成：

- 多 endpoint 真多副本 fan-out
- 冲突策略化处理
- 自动重试从无限重试升级为：
  - 最大重试次数上限
  - 自动重试冷却时间

价值：

- 复制语义从“能发出去”提升为“多副本实际分发”
- 冲突处理从“单一硬失败”提升为“运行时可选策略”
- 重试行为从“无上限、可能热循环”提升为“可控、可预期”

### 4.3 P2 级

已完成：

- include/exclude/filter 接入真实主链路
- monitor HTTP 自动化测试
- monitor 浏览器 smoke 与前端动作修复
- 上传中状态与分片进度暴露
- 最近完成/最近失败上传历史
- 大文件策略显式化：
  - `uploadBlockSizeBytes`
- 失败项可观测性增强：
  - `retryCount`
  - `failedAtMillis`
  - `lastRetriedAtMillis`
  - 失败原因汇总
  - 热点失败项
  - 队列类型矩阵
  - 最近操作时间线
  - 首页信息结构重排
  - failed 项 `retryable` / `remainingRetries`

价值：

- 监控从“只看失败队列”升级为“能看同步过程、失败状态、重试状态、上传历史”
- 大文件链路从“底层已有但上层不可见”升级为“配置和页面都可见”

## 5. 当前完善度判断

### 5.1 强项

- 主链路关键语义已经基本补齐，尤其是上传校验、finalize、rename、fan-out、冲突处理
- 关键回归测试已经不只是单元级别，而是覆盖到 HTTP、浏览器 smoke、双节点 E2E
- 监控面已经形成体系，不再只有失败列表，具备初步运维价值
- 自动重试策略已经从“无限重试”收敛到“有限 + 退避 + 人工介入保留”

### 5.2 薄弱点

- 多节点验证仍偏“最小闭环”，距离复杂拓扑/多副本一致性验证还有距离
- 冲突分类仍然较粗，尚未形成“原因 -> 建议动作”的明确映射
- 失败项虽然能看见状态，但还没有形成更完整的人工恢复工作流
- 大文件能力仍主要依赖底层 `p2p-transfer` 自动分片，`p2p-sync` 侧尚未形成更显式的策略抽象

### 5.3 当前阶段判断

如果按工程阶段来划分，当前更接近：

- 不是“实验性原型”
- 也还不是“高强度生产级多节点同步平台”
- 而是“具备较强工程闭环和可维护性基础的可用版本”

## 6. 风险与剩余缺口

### 6.1 功能缺口

- 缺少更丰富的多节点 fan-out 场景验证
- 缺少失败项自动恢复与人工恢复的更细粒度策略
- 缺少失败趋势、时间窗口趋势、恢复成功率等更高层指标
- 缺少更显式的大文件策略表达，例如分片阈值、策略模式、重试策略说明的一体化展示

### 6.2 工程风险

- 当前不少增强依赖当前工作区上下文和连续迭代结果，新成员如果只看代码，理解成本仍然偏高
- monitor 信息虽然已经丰富，但后续如果继续堆字段，不做抽象会再次膨胀
- 自动重试与人工重试已经分流，但还缺少更正式的“自动策略不限制人工”的文档说明

### 6.3 文档风险

- 现有项目文档对 `p2p-sync` 的这些增强覆盖仍不足
- 当前报告能作为阶段性总结，但还需要后续同步到架构/工作流类文档中

## 7. 建议的后续优先级

### 7.1 建议优先继续做的事项

1. 多节点 fan-out 更强验证覆盖
2. failed 项分级展示：可自动恢复 / 需人工介入
3. monitor 总览中显式展示当前重试策略参数
4. 失败趋势与恢复成功率统计

### 7.2 可以延后但值得规划的事项

1. 大文件策略模型进一步显式化
2. 更细粒度冲突类型与推荐处置动作
3. 更系统的 monitor 前端交互测试

## 8. 验证情况摘要

本阶段已多次通过以下类型验证：

- `p2p-sync` 定向单元测试
- `P2PDirectorySyncE2ETest` 双节点 E2E
- `P2PSyncMonitorServerTest` HTTP 自动化测试
- monitor 浏览器 smoke
- `RpcSyncEventHandlerTest` 上传状态/分片进度验证
- `P2PSyncQueueEngineTest` 重试次数与退避语义验证
- `P2PSyncConfigTest` 配置项加载验证

## 9. 当前工作区附注

截至本文档生成时，工作区还包含一组已验证但未提交的 monitor 调整：

- 保留 failed 项的手动“重试(覆盖同步)”按钮
- 即使 failed 项已经达到自动重试上限，人工重试仍然不受限制
- `retryable` / `remainingRetries` 仅作为提示信息，不作为人工操作限制

这组调整与当前自动重试策略并不冲突，属于“自动受控、人工保留兜底”的设计。

## 10. 总结

文件同步能力这条主线已经完成了从“可跑通”到“可验证、可观察、可控”的关键跃迁。

当前最值得肯定的不是某一个单点功能，而是以下三件事已经同时成立：

- 主链路关键语义更完整
- 回归测试更可信
- monitor 可观测性足以支撑问题定位和人工处置

接下来的重点不再是盲目加字段，而是把现有能力进一步整理成更清晰的策略、分级和操作闭环。
